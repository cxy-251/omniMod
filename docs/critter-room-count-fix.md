## 用户现象与证据

用户报告放生点在本星球及生态舱中显示四十多只，但可见约十只；哈奇数量稀疏且房间地面没有蛋，仍有“狭窄”。当前 Player.log 已实际加载 load21、读入第 256 周期存档并继续运行到第 258 周期，本轮未出现此前共享泛型 GoTo 的类型转换异常。

只读检查最新存档发现，共享实体池中有 56 枚普通哈奇蛋、95 枚石壳哈奇蛋、33 枚金属哈奇蛋等，实体位置仍保留多个星球／舱室坐标。原版 EggConfig 为蛋创建 spaceRequiredPerCreature=0 的 OvercrowdingMonitor；UpdateState 仍先执行 UpdateRegion，再在空间需求为零时返回。UpdateRegion 无存储检查，按实体坐标将它加入 cavity.eggs；房间 Occupancy.Analyze 随后把这些蛋按孵化后的动物空间计入 HatchedEggOccupiedCellCount，FutureOvercrowded 即中文“狭窄”。因此地面没有可见蛋，也会受到共享库存中蛋的错误占位。

放生点的原版 BaggableCritterCapacityTracker 按 cavity.creatures 列表逐条累加（带原版物种筛选和袋装／陷阱排除）；不验证实体仍在该房间，也不去重。原版 AddToCavity 无去重，而 RemoveFromCavity 只移除一条；这些是可能放大／残留计数的缺口。当前只读存档无法读取运行时 CavityInfo 列表，不能据此声称已观测到“四十多只→十只”的实际修正值。

## 修改

- 仅对 OmniEntityPool 与 GlobalItemCollector 门户存储中的实体阻止原版 UpdateRegion 重新挂回本地空间，移除已有房间登记并使分析缓存失效。鱼类蛋还退出 FishOvercrowingManager 的全局水生实体列表，避免被重新纳入鱼池。实际出库到地面或孵化器后自动恢复原版登记，不重写坐标、蛋状态或存档，不销毁实体。
- 房间登记表按 Unity 实体身份去重，排除销毁、位置已离开房间、共享库实体及错误种类记录。移除错误记录时同步失效实体的 cavity 缓存，保证同房间出库也能重新登记；去重时保留仍有效的那份登记。普通存储中的动物不从原版占位表强行删除，保留原版拥挤规则。
- 放生点、取出点及水生容量统计按当前房间／鱼池的实际实体位置去重，保留原版物种筛选、袋装与陷阱排除；存储中的动物不计入可放养数量。该逻辑同时用于 UI 数量与实际容量判断，不只是改显示数字。
- 在 AddToCavity 与鱼池 Add 入口阻止重复登记。修正已有房间记录后把 occupancy 标为 dirty，让原版重新计算拥挤和“狭窄”；普通地面和孵化器内的蛋仍按原版规则计入未来空间。没有修改动物空间需求、繁殖效果、房间面积或建筑数量上限。
- 按房间使用弱引用缓存，每个房间最多约一秒清理一次已有名册；不扫描全图动物，不额外创建逐帧调度。仅实际清理记录时输出限频日志，包含动物／蛋清理数、当前名册和房间面积。运行时缓存不写入存档。

全部新补丁挂在明确声明的非泛型方法上，不拦截共享 GenericInstance.GoTo；保留 load21 的读档修复和 fish22 的鱼苗自动打包。
